# 第一部分：先建立全局认知

## 1.1 什么是架构？

架构不是"用什么框架"，而是：

> **系统的形状**——由哪些部分组成、部分之间如何通信、谁负责什么、数据如何流动、如何应对变化和规模。

一个常用的比喻：

- **代码** = 砖块
- **框架** = 预制板
- **架构** = 整栋楼的设计图（承重、水电、消防、扩展）

架构决策通常是最难更改的，所以要在早期想清楚。

## 1.2 架构关注的两大维度

| 维度             | 含义                 | 例子                   |
| ---------------- | -------------------- | ---------------------- |
| **结构性** | 系统由哪些组件构成   | 分层、微服务、事件驱动 |
| **横切性** | 贯穿所有组件的关注点 | 安全、日志、监控、性能 |

## 1.3 好架构的目标

- **可维护性**：改一处不影响全局
- **可扩展性**：流量涨了能扛住
- **可测试性**：能自动化验证
- **可部署性**：能快速、安全地上线
- **可观测性**：出问题能定位

# 第二部分：从零开始——单体分层架构

这是最应该先学透的架构，因为后面所有架构都是它的演化。

## 2.1 三层架构详解

```
┌─────────────────────────┐
│   表现层 Presentation    │  用户看到/操作的界面
├─────────────────────────┤
│   业务层 Business        │  核心规则、计算、流程
├─────────────────────────┤
│   数据层 Data Access     │  读写数据库
└─────────────────────────┘
```

### 表现层

- 接收用户请求（HTTP、WebSocket）
- 参数校验、格式化
- 调用业务层，返回响应

**例子**（Node.js + Express）：

```js
app.post('/orders', async (req, res) => {
  const { userId, items } = req.body;
  const order = await orderService.createOrder(userId, items);
  res.json(order);
});
```

### 业务层

- 业务规则：比如"库存不足不能下单"
- 事务：扣库存 + 创建订单要么都成功要么都失败
- 编排：调用多个数据操作

```js
class OrderService {
  async createOrder(userId, items) {
    await this.checkStock(items);
    const order = await this.orderRepo.create(userId, items);
    await this.stockRepo.decrease(items);
    return order;
  }
}
```

### 数据层

- 封装数据库操作
- 提供 Repository / DAO 接口

```js
class OrderRepository {
  async create(userId, items) {
    return db.insert('orders', { userId, items });
  }
}
```

## 2.2 为什么要分层？

- **职责单一**：每层只做一件事
- **可替换**：换数据库只改数据层
- **可测试**：业务层可以 mock 数据层

## 2.3 单体的优缺点

| 优点     | 缺点                  |
| -------- | --------------------- |
| 开发简单 | 代码耦合              |
| 部署容易 | 扩展只能整体扩展      |
| 调试方便 | 一处 bug 可能拖垮全站 |
| 事务简单 | 团队协作冲突多        |

> **学习建议**：先用单体把业务跑通，不要一上来就微服务。

# 第三部分：前后端分离

## 3.1 传统模式 vs 分离模式

**传统**：后端渲染 HTML（JSP、Thymeleaf、Django Template）

**分离**：

```
前端（React/Vue） ──HTTP/JSON──> 后端 API ──> 数据库
```

## 3.2 关键点

- **API 契约**：REST / GraphQL / gRPC
- **认证**：JWT、Session、OAuth2
- **跨域**：CORS
- **状态管理**：前端 Redux/Pinia，后端无状态

## 3.3 REST vs GraphQL

|          | REST          | GraphQL          |
| -------- | ------------- | ---------------- |
| 数据获取 | 多个端点      | 单端点，按需查询 |
| 过度获取 | 常见          | 可避免           |
| 缓存     | HTTP 缓存简单 | 需额外方案       |
| 学习曲线 | 低            | 中               |

**REST 例子**：

```
GET /users/1
GET /users/1/orders
```

**GraphQL 例子**：

```graphql
query {
  user(id: 1) {
    name
    orders { id total }
  }
}
```

# 第四部分：微服务架构

## 4.1 从单体到微服务

单体变大后的痛点：

- 代码库巨大，编译慢
- 一个小改动要全量部署
- 团队互相阻塞
- 无法针对性扩展

微服务思路：**按业务能力拆分**。

```
         ┌─────────────┐
         │  API 网关    │
         └──────┬──────┘
    ┌───────────┼───────────┐
    ▼           ▼           ▼
┌────────┐ ┌────────┐ ┌────────┐
│ 用户服务│ │ 订单服务│ │ 库存服务│
└────────┘ └────────┘ └────────┘
    │           │           │
   DB          DB          DB
```

## 4.2 微服务的核心挑战

### 1. 服务通信

- **同步**：HTTP / gRPC
- **异步**：消息队列（Kafka、RabbitMQ）

### 2. 数据一致性

- 每个服务独立数据库
- 跨服务事务 → **Saga 模式**
  - 把大事务拆成多个本地事务
  - 失败时执行补偿操作

### 3. 服务发现

- 服务实例动态变化
- 工具：Consul、Eureka、Kubernetes Service

### 4. 容错

- **熔断**：失败太多就快速返回
- **限流**：保护自己不被压垮
- **降级**：非核心功能暂时关闭
- 工具：Hystrix、Sentinel、Resilience4j

### 5. 可观测性

- **日志**：ELK / Loki
- **指标**：Prometheus + Grafana
- **链路追踪**：Jaeger、Zipkin、OpenTelemetry

## 4.3 什么时候该用微服务？

✅ **适合**：

- 团队规模大（多个团队独立开发）
- 业务复杂度高
- 需要独立扩展不同模块
- 有成熟 DevOps 能力

❌ **不适合**：

- 小团队、早期项目
- 没有自动化部署
- 业务还没稳定

> **马丁·福勒的建议**：不要一上来就微服务，先单体，等痛了再拆。

# 第五部分：事件驱动架构

## 5.1 核心思想

组件之间不直接调用，而是通过**事件**通信。

```
订单服务 ──发布 "订单已创建"──> 消息队列
                                    │
                    ┌───────────────┼───────────────┐
                    ▼               ▼               ▼
                库存服务        通知服务        积分服务
```

## 5.2 关键概念

- **生产者**：发布事件
- **消费者**：订阅并处理
- **Broker**：Kafka、RabbitMQ、AWS SNS/SQS
- **事件 vs 命令**：
  - 事件 = "发生了什么"（过去时）
  - 命令 = "请做什么"（祈使句）

## 5.3 优缺点

| 优点       | 缺点           |
| ---------- | -------------- |
| 松耦合     | 调试困难       |
| 高扩展     | 事件顺序难保证 |
| 异步、削峰 | 需要处理幂等   |
| 实时响应   | 最终一致性     |

## 5.4 常见模式

- **发布/订阅**：一对多广播
- **事件溯源（Event Sourcing）**：状态由事件序列重建
- **CQRS**：读写分离，写用命令模型，读用查询模型

# 第六部分：其他重要架构

## 6.1 Serverless（无服务器）

- 只写函数，云平台管运行
- 例子：AWS Lambda、Vercel Functions、Cloudflare Workers
- 适合：事件触发、定时任务、轻量 API
- 缺点：冷启动、供应商锁定

## 6.2 JAMstack

- **J**avaScript + **A**PIs + **M**arkup
- 静态站点 + 无头 CMS + CDN
- 例子：Next.js、Gatsby、Hugo
- 优点：快、安全、便宜

## 6.3 微前端

- 把前端拆成多个独立小应用
- 每个团队独立开发部署
- 工具：Module Federation、qiankun、single-spa

# 第七部分：横切关注点（每个架构都要考虑）

## 7.1 安全

- **认证**：你是谁 → JWT、Session、OAuth2
- **授权**：你能做什么 → RBAC、ABAC
- **传输**：HTTPS
- **防护**：XSS、CSRF、SQL 注入、限流

## 7.2 性能

- **缓存**：浏览器 → CDN → 应用缓存 → 数据库缓存
- **异步**：消息队列削峰
- **数据库优化**：索引、分库分表、读写分离
- **CDN**：静态资源就近分发

## 7.3 可用性

- **冗余**：多实例、多机房
- **负载均衡**：Nginx、HAProxy、云 LB
- **健康检查**：自动摘除故障节点
- **熔断降级**：保护核心链路

## 7.4 可观测性

三大支柱：

- **Logs**：发生了什么
- **Metrics**：数量、趋势
- **Traces**：请求经过了哪些服务

## 7.5 CI/CD

```
代码提交 → 构建 → 测试 → 部署 → 监控
```

- 工具：GitHub Actions、GitLab CI、Jenkins、ArgoCD

# 第八部分：学习路径建议

## 阶段 1：基础（1-2 个月）

- HTTP、REST、JSON
- 三层架构，动手写一个单体应用
- 数据库基础（SQL、索引、事务）
- 前端基础（HTML/CSS/JS + 一个框架）

## 阶段 2：进阶（2-3 个月）

- 前后端分离，写一个完整项目
- 认证授权（JWT、OAuth2）
- 缓存（Redis）、消息队列（RabbitMQ/Kafka）
- Docker 容器化
- CI/CD 基础

## 阶段 3：分布式（3-6 个月）

- 微服务拆分实践
- 服务发现、网关、配置中心
- 分布式事务（Saga）
- 可观测性（Prometheus + Grafana + Jaeger）
- Kubernetes 基础

## 阶段 4：架构思维（持续）

- 读经典书：
  - 《架构整洁之道》
  - 《数据密集型应用系统设计》
  - 《微服务架构设计模式》
  - 《领域驱动设计》
- 参与真实项目，做架构决策
- 学习系统设计面试题（如 Alex Xu 的书）

# 第九部分：动手项目建议

按难度递进：

1. **Todo List**：单体 + 数据库 → 理解 CRUD
2. **博客系统**：前后端分离 + JWT → 理解 API 设计
3. **电商 Demo**：多服务 + 消息队列 → 理解微服务
4. **短链服务**：缓存 + 分库分表 → 理解高性能
5. **聊天系统**：WebSocket + 事件驱动 → 理解实时通信

每个项目都问自己：

- 如果流量涨 100 倍怎么办？
- 如果某个服务挂了怎么办？
- 如果要做多机房怎么办？
