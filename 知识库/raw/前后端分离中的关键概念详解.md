# 前后端分离中的关键概念详解

这四点都是前后端分离架构中**必须理解的核心概念**。下面逐个讲透。

---

## 一、API 契约：REST / GraphQL / gRPC

**"契约"** = 前后端约定好的通信规则：用什么格式、怎么调用、返回什么。

### 1. REST

**核心思想**：用 HTTP 动词 + URL 资源来表达操作。

```
GET    /users       → 获取用户列表
GET    /users/1     → 获取 id=1 的用户
POST   /users       → 创建用户
PUT    /users/1     → 全量更新用户
PATCH  /users/1     → 部分更新
DELETE /users/1     → 删除用户
```

**特点**：

- 基于 HTTP 语义，直观易懂
- 用状态码表达结果（200 成功、404 找不到、500 服务器错误）
- 通常返回 JSON
- 每个资源一个端点

**优点**：简单、通用、缓存友好
**缺点**：容易"过度获取"（拿一堆用不到的数据）或"多次请求"（要拼多个接口）

**例子**：

```http
GET /users/1/orders  ← 请求行（客户端发给服务器）
Response:            ← 响应（服务器返回给客户端）
[
  { "id": 1, "total": 100, "items": [...] },
  { "id": 2, "total": 200, "items": [...] }
]
```

---

### 2. GraphQL

**核心思想**：只用一个端点，前端**按需声明**要什么字段。

```graphql
POST /graphql

query {
  user(id: 1) {
    name
    orders {
      id
      total
    }
  }
}
```

**返回**：

```json
{
  "data": {
    "user": {
      "name": "张三",
      "orders": [
        { "id": 1, "total": 100 },
        { "id": 2, "total": 200 }
      ]
    }
  }
}
```

**特点**：

- 单端点，前端精确控制返回字段
- 强类型 Schema（前后端共享类型定义）
- 支持一次请求拿多个资源

**优点**：避免过度获取、减少请求次数
**缺点**：缓存复杂、学习曲线高、复杂查询可能拖垮后端（需要限流/深度限制）

---

### 3. gRPC

**核心思想**：用 **Protocol Buffers**（二进制）通信，性能极高。

```proto
// 定义契约
service UserService {
  rpc GetUser (UserRequest) returns (User);
}

message UserRequest {
  int32 id = 1;
}

message User {
  int32 id = 1;
  string name = 2;
}
```

**特点**：

- 基于 HTTP/2，支持双向流
- 二进制传输，比 JSON 小、快
- 自动生成客户端/服务端代码
- 强类型

**优点**：高性能、跨语言、适合微服务内部通信
**缺点**：浏览器支持有限（需要 gRPC-Web）、调试不如 JSON 直观

---

### 三者对比

| 维度       | REST     | GraphQL      | gRPC               |
| ---------- | -------- | ------------ | ------------------ |
| 传输格式   | JSON     | JSON         | Protobuf（二进制） |
| 端点       | 多端点   | 单端点       | 多方法             |
| 性能       | 中       | 中           | 高                 |
| 学习曲线   | 低       | 中           | 中高               |
| 浏览器支持 | 好       | 好           | 需 gRPC-Web        |
| 典型场景   | 通用 API | 前端灵活查询 | 微服务内部通信     |

**实际选择**：

- 对外 API → REST
- 前端复杂数据需求 → GraphQL
- 微服务之间高性能调用 → gRPC

---

## 二、认证：JWT / Session / OAuth2

**"认证"** = 验证"你是谁"。核心问题：**用户登录后，后续请求怎么证明身份？**

### 1. Session（会话）

**原理**：服务器保存用户状态，客户端只存一个 Session ID。

```
1. 用户登录 → 服务器创建 Session，存到内存/Redis
2. 服务器返回 Set-Cookie: sessionId=abc123
3. 后续请求浏览器自动带 Cookie: sessionId=abc123
4. 服务器查 Session 表，找到对应用户
```

**流程**：

```
客户端                    服务器
  │  POST /login           │
  │ ─────────────────────> │ 创建 session
  │  Set-Cookie: sid=abc   │ 存 Redis
  │ <───────────────────── │
  │                        │
  │  GET /profile          │
  │  Cookie: sid=abc       │
  │ ─────────────────────> │ 查 Redis 验证
  │ <───────────────────── │
```

**优点**：服务器可控（能强制下线）、实现简单
**缺点**：服务器要存状态（分布式需 Redis）、跨域麻烦

---

### 2. JWT（JSON Web Token）

**原理**：把用户信息编码成一个**签名令牌**，服务器不存状态。

**结构**（三段，用 `.` 分隔）：

```
Header.Payload.Signature

eyJhbGciOiJIUzI1NiJ9.eyJ1c2VySWQiOjEsImV4cCI6MTcwMDAwMDAwMH0.签名
```

- **Header**：算法类型
- **Payload**：用户数据（如 `{ userId: 1, exp: 过期时间 }`）
- **Signature**：用密钥签名，防篡改

**流程**：

```
1. 登录成功 → 服务器生成 JWT 返回
2. 客户端存起来（localStorage / Cookie）
3. 后续请求带 Authorization: Bearer <token>
4. 服务器验签，直接读出用户信息（无需查库）
```

**优点**：无状态、易扩展、跨域友好
**缺点**：无法主动失效（除非用黑名单）、token 泄露风险、payload 是明文（不能放敏感信息）

---

### 3. OAuth2（授权框架）

**注意**：OAuth2 是**授权**，不是认证（虽然常配合认证用）。

**场景**：第三方应用想访问你的资源，但不该拿到你的密码。

**典型例子**："用微信登录"、"用 GitHub 登录"。

**核心角色**：

- **资源所有者**：你
- **客户端**：第三方应用
- **授权服务器**：微信/GitHub
- **资源服务器**：存你数据的服务

**授权码模式流程**：

```
1. 应用跳转微信授权页
2. 用户同意授权
3. 微信返回授权码 code
4. 应用用 code 换 access_token
5. 应用用 token 访问资源
```

**常见模式**：

- **授权码模式**：最安全，用于有后端的应用
- **简化模式**：用于纯前端
- **密码模式**：用户直接给账号密码（不推荐）
- **客户端模式**：服务间通信

**JWT vs OAuth2 关系**：

- OAuth2 是**流程/框架**
- JWT 是**令牌格式**
- 可以用 JWT 作为 OAuth2 的 access_token

---

### 三者对比

|          | Session  | JWT                 | OAuth2     |
| -------- | -------- | ------------------- | ---------- |
| 状态     | 服务器存 | 无状态              | 取决于实现 |
| 存储     | Cookie   | localStorage/Cookie | Token      |
| 主动失效 | 容易     | 难                  | 支持       |
| 跨域     | 麻烦     | 好                  | 好         |
| 用途     | 单体应用 | API 认证            | 第三方授权 |

**实际选择**：

- 传统 Web → Session
- 前后端分离 / 移动端 → JWT
- 第三方登录 / 开放平台 → OAuth2

## 三、跨域：CORS

### 什么是"跨域"？

浏览器的**同源策略**：只有**协议 + 域名 + 端口**完全相同的请求才允许。

```
https://a.com  →  https://a.com/api     ✅ 同源
https://a.com  →  http://a.com/api      ❌ 协议不同
https://a.com  →  https://b.com/api     ❌ 域名不同
https://a.com  →  https://a.com:8080    ❌ 端口不同
```

**为什么有同源策略**：防止恶意网站偷取你的数据（比如你在银行网站的登录态）。

### CORS 是什么？

**CORS（Cross-Origin Resource Sharing）** = 服务器告诉浏览器"我允许哪些跨域请求"。

### 简单请求 vs 预检请求

**简单请求**（GET/POST + 简单头）→ 直接发，服务器返回 `Access-Control-Allow-Origin` 即可。

**复杂请求**（PUT/DELETE、自定义头、JSON）→ 先发一个 **OPTIONS 预检请求**：

```
浏览器 → 服务器：OPTIONS /api
  Origin: https://a.com
  Access-Control-Request-Method: PUT

服务器 → 浏览器：
  Access-Control-Allow-Origin: https://a.com
  Access-Control-Allow-Methods: PUT, POST
  Access-Control-Allow-Headers: Content-Type
  Access-Control-Max-Age: 86400
```

预检通过后，才发真正的请求。

### 关键响应头

| 头                                   | 作用              |
| ------------------------------------ | ----------------- |
| `Access-Control-Allow-Origin`      | 允许哪些源        |
| `Access-Control-Allow-Methods`     | 允许哪些方法      |
| `Access-Control-Allow-Headers`     | 允许哪些请求头    |
| `Access-Control-Allow-Credentials` | 是否允许带 Cookie |
| `Access-Control-Max-Age`           | 预检结果缓存多久  |

### 常见解决方案

1. **后端设置 CORS 头**（推荐）
2. **开发环境用代理**（Vite/Webpack devServer proxy）
3. **Nginx 反向代理**（同源转发）
4. **JSONP**（只支持 GET，已过时）

## 四、状态管理

### 前端状态管理

**"状态"** = 应用运行时需要记住的数据（用户信息、购物车、UI 状态等）。

**为什么需要管理**：

- 组件多了，数据传递混乱（props 层层传递）
- 多个组件需要共享同一份数据
- 需要追踪数据变化

### Redux（React 生态）

**核心思想**：单一数据源 + 纯函数更新。

```
Action → Reducer → Store → View
  ↑                            │
  └──────── 用户操作 ───────────┘
```

**三个原则**：

1. **单一数据源**：整个应用状态存在一个 Store
2. **状态只读**：只能通过 dispatch action 修改
3. **纯函数修改**：reducer 是纯函数

**例子**：

```js
// Action
const addTodo = (text) => ({ type: 'ADD_TODO', payload: text });

// Reducer
function todos(state = [], action) {
  switch (action.type) {
    case 'ADD_TODO':
      return [...state, { text: action.payload, done: false }];
    default:
      return state;
  }
}

// 使用
dispatch(addTodo('学习架构'));
```

**优点**：可预测、易调试（时间旅行）、生态成熟
**缺点**：样板代码多、学习曲线陡

### Pinia（Vue 生态）

**Vue 3 官方推荐**，比 Vuex 更简洁。

```js
export const useCartStore = defineStore('cart', {
  state: () => ({ items: [] }),
  getters: {
    total: (state) => state.items.reduce((s, i) => s + i.price, 0),
  },
  actions: {
    addItem(item) {
      this.items.push(item);
    },
  },
});
```

**优点**：API 简洁、TypeScript 友好、无 mutation 概念
**缺点**：仅限 Vue

### 其他方案

- **Zustand**：轻量，React 社区新宠
- **MobX**：响应式，自动追踪依赖
- **Recoil/Jotai**：原子化状态
- **Context API**：React 内置，适合简单场景

### 后端"无状态"

**"无状态"** = 服务器不保存客户端会话信息，每个请求自带全部所需信息。

**对比**：

|            | 有状态       | 无状态           |
| ---------- | ------------ | ---------------- |
| 服务器存储 | 保存 session | 不保存           |
| 扩展性     | 需共享存储   | 任意实例都能处理 |
| 典型       | Session      | JWT              |

**为什么后端要无状态**：

- 水平扩展容易（加机器就行）
- 负载均衡不需要 sticky session
- 容错性好（一台挂了，请求转其他台）

**做法**：

- 用 JWT 替代 Session
- 会话数据放 Redis（共享存储）
- 文件放对象存储（S3/OSS）

---

## 总结：一张表理清

| 概念               | 解决的问题       | 关键技术                     |
| ------------------ | ---------------- | ---------------------------- |
| **API 契约** | 前后端怎么通信   | REST / GraphQL / gRPC        |
| **认证**     | 你是谁           | JWT / Session / OAuth2       |
| **跨域**     | 浏览器同源限制   | CORS                         |
| **状态管理** | 数据怎么存和共享 | 前端 Redux/Pinia；后端无状态 |

3. **然后跨域**：前端 3000 端口，后端 8080 端口，亲手解决 CORS
